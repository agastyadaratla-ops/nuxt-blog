Norvik is at version 0.0.1, and version 0.0.1 means exactly one thing: the kernel boots under GRUB and writes text to the screen. Six files, about four kilobytes, no standard library, no operating system underneath it.

The README describes a much larger ambition. This post is about the four kilobytes that actually exist, because the gap between the two is the honest part.

The goal

Get a machine to run code I wrote, with nothing in between. Not a program running on an OS, but the thing the bootloader hands control to. Everything after that (keyboard, memory management, a filesystem) depends on getting this first step right, and the first step is mostly about convincing a set of tools to stop being helpful.

The decisions

Use GRUB and Multiboot instead of writing a bootloader. Writing a real bootloader means 16 bit real mode, BIOS interrupts, the 512 byte boot sector limit, and then switching the CPU to protected mode by hand. GRUB has done all of it. The price is a header GRUB looks for in the first 8KB of the binary:

.set MAGIC,    0x1BADB002
.set FLAGS,    0
.set CHECKSUM, -(MAGIC + FLAGS)

The magic number is fixed by the spec. The checksum exists so that the three fields sum to zero, which is how GRUB confirms it has found a real header rather than a coincidence. Flags is 0, meaning nothing extra is requested yet.

Build with an i686-elf cross compiler. The system compiler targets the host OS: it assumes libc exists, that there is a program loader, that main is called by something. A cross compiler targeting bare ELF assumes none of that. The flags finish the job:

CFLAGS = -ffreestanding -O2 -Wall
# link: -nostdlib -lgcc

-ffreestanding tells GCC there is no standard library and that it must not assume the usual meaning of functions. -nostdlib keeps the linker from pulling in a C runtime that would try to set up an environment that does not exist. -lgcc is added back deliberately, because GCC emits calls to its own helper routines for things like 64 bit division, and those still have to resolve.

Load at the one megabyte mark. The linker script starts the image at 0x100000:

. = 0x100000;

.text BLOCK(4K) : ALIGN(4K) {
    *(.multiboot)
    *(.text)
}

Below 1MB is a museum of memory mapped hardware and BIOS structures. Above it is ordinary RAM. The .multiboot section is placed first inside .text on purpose, so the header lands where GRUB will look for it.

Write to VGA text memory directly. There is no screen driver and no console. There is a buffer at 0xB8000 where every character is two bytes: the ASCII code, then a colour attribute. 0x0F is white on black. Writing a byte there puts a letter on the display.

What I found reading it back

These are things I can see in the code rather than problems I hit and solved, so they belong on a to do list rather than in a war story.

The screen output is wrong, and it is a one word bug. print declares its cursor inside the function:

void print(const char* str) {
    int i = 0;
    int pos = 0;      // resets on every call
    ...
}

kernel_main calls it twice, so the second call starts writing at position zero again and paints over the first. "Norvik 0.0.1" is twelve characters and " - Welcome." is eleven, so what actually reaches the screen is " - Welcome.1", with that trailing 1 being the only surviving character of the first string. The fix is to make the cursor outlive the call, either as a file scope variable or as static int pos.

No stack is set up before C code runs. _start calls straight into kernel_main:

_start:
    call kernel_main

A call pushes a return address, and C needs a stack for locals. The Multiboot spec explicitly says the OS image must create its own stack, so relying on whatever value GRUB left in esp is undefined behaviour that happens to work. The standard fix is to reserve space in .bss and point esp at the top of it before calling anything.

The VGA pointer should be volatile. Nothing ever reads back from 0xB8000, so those writes have no observable effect as far as the optimiser is concerned. GCC keeps them here in practice, but marking the pointer volatile is what actually guarantees it, and memory mapped hardware is the exact case the keyword exists for.

What comes next

Keyboard input is the next item on the roadmap, and it needs an interrupt descriptor table before it can work. Memory management after that will need real numbers about available RAM, which means setting bit 1 in the Multiboot flags so GRUB provides a memory map, rather than the current flags value of 0.
