Snake, except you steer it by holding fingers up to a webcam. One finger sends it up, two down, three right, four left. It runs entirely in a browser tab, in about 250 lines across three files, with no build step.

The goal

Replace the input on a game everyone already understands, and see how much of the difficulty lives in the recognition rather than the game.

Snake is well chosen for this, and the reason is the size of its control surface. There are four directions. There is no timing, no analogue precision, no combinations, and no penalty for a slightly late input because the snake keeps moving anyway. A gesture system that is only roughly right still produces a playable game. Try the same thing on a platformer and every missed frame is a death.

The decisions

MediaPipe Hands, loaded straight from a CDN. No bundler, no install, no package.json. Three files and an index.html you can double click. For a project whose entire purpose is to see whether an idea is fun, spending the first evening on a build pipeline is the wrong order of operations.

The model runs with one hand, and detection and tracking confidence both at 0.6. One hand because the game only needs one number, and a second hand entering the frame is far more likely to be noise than intent.

Count fingers geometrically instead of classifying gestures. MediaPipe hands back 21 landmarks per hand. The obvious move is to feed those landmarks to a classifier. I did not, because the thing I needed to know is much smaller than what a classifier answers.

const fingerTips = [8, 12, 16, 20];
const fingerPips = [6, 10, 14, 18];
let raised = 0;
for (let i = 0; i < fingerTips.length; i++) {
  if (landmarks[fingerTips[i]].y < landmarks[fingerPips[i]].y) raised++;
}

If a fingertip sits higher on the screen than its own middle knuckle, that finger is up. Four comparisons. No training data, no second model, no inference cost beyond what MediaPipe has already spent, and nothing to debug except an inequality.

The thumb is deliberately left out. A thumb does not fold along the same axis as the other four, so the tip above knuckle test does not describe it, and including it would have meant special casing the one finger that behaves differently in order to gain a fifth gesture the game has no use for.

Guard direction changes on the current axis. Each mapping carries a condition:

if (raised === 1 && direction.y === 0) direction = { x: 0, y: -1 };

A snake already travelling vertically will not accept another vertical instruction. That single clause is what stops it folding back into its own neck, which in a keyboard version is the classic way to lose to your own hand rather than to the game. It needs no input queue and no extra state, because the current direction already holds all the information required.

Two loops, running at different speeds

The most interesting property of this project was not designed. It fell out of using two independent timers.

MediaPipe fires onResults on every camera frame, roughly thirty times a second. The game ticks on a setInterval every 200 milliseconds, so five times a second. Nothing synchronises them.

The consequence is that the direction variable can be rewritten five or six times between one movement of the snake and the next, and only the last write before a tick has any effect on the game. Every intermediate value is silently discarded.

That turns out to be why the controls feel forgiving. Changing your hand from one finger to three passes through two on the way, and your fingers do not all arrive at once. All of that mess happens inside a single tick and is thrown away. You get roughly a fifth of a second of wobble, and only where your hand settles counts.

If the game ran its logic on every camera frame instead, the same hand movement would send the snake through two or three unwanted turns before reaching the one you meant.

Where it is fragile

The finger test assumes an upright hand. It compares y coordinates and nothing else. Rotate your hand ninety degrees and a raised finger is no longer above its knuckle, so the count collapses towards zero and the snake stops responding. Measuring each fingertip's distance from the wrist instead of its height would make the test rotation invariant, at the cost of a square root per finger.

There is no debounce. The 200ms tick hides most of the transitional noise, as described above, but not all of it. If a tick lands exactly while your fingers are passing through two on the way to three, the snake turns and it was not what you asked for. Requiring the same count on two consecutive frames before committing would remove that without any felt lag, because the game only reads direction five times a second anyway.

There is a variable called lastGesture in the file, initialised and never read again. It is the start of exactly that debounce.

Food can spawn inside the snake. The replacement position is a plain random tile with no check against the body, so on a long snake it can appear underneath one of its own segments. The fix is a loop that rerolls until the chosen tile is not occupied, which is fine on a twenty by twenty grid where the snake will never be long enough for that loop to be slow.

What I would change first

The debounce, because it is the largest gain for the least work and the variable is already sitting there waiting for it.

After that, the rotation invariant finger test, which is the difference between a demo that works when you hold your hand the way the author did and one that works when someone else tries it.
