Snake, except you steer it by holding up fingers to a webcam. One finger sends it up, two down, three right, four left. It runs entirely in a browser tab, in about 250 lines across three files.

The goal

Take a game everyone already understands and replace the input with something that is not a keyboard. Snake is a good target for this because the control surface is tiny: four directions, no timing, no analogue precision. If the gesture recognition is even roughly right, the game is playable.

The decisions

MediaPipe Hands, loaded from a CDN. No build step, no bundler, no install. Three files and an index.html you can open. The model is configured for one hand, with detection and tracking confidence both at 0.6.

Count fingers geometrically rather than classifying gestures. MediaPipe returns 21 landmarks per hand. Rather than training or importing a gesture classifier, the code compares each fingertip against the joint two positions below it:

const fingerTips = [8, 12, 16, 20];
const fingerPips = [6, 10, 14, 18];
let raised = 0;
for (let i = 0; i < fingerTips.length; i++) {
  if (landmarks[fingerTips[i]].y < landmarks[fingerPips[i]].y) raised++;
}

If a fingertip sits higher on the screen than its own knuckle, that finger is up. Four comparisons, no model, no training data. The thumb is deliberately ignored, which sidesteps the hardest finger to read this way.

Guard against reversing into yourself. Each direction change is conditional on the current axis:

if (raised === 1 && direction.y === 0) direction = { x: 0, y: -1 };

A snake travelling vertically cannot accept another vertical instruction, so it can never fold back into its own neck. Two lines of state, no separate input queue.

What is actually going on underneath

There are two loops running at very different speeds, and they are not synchronised.

MediaPipe fires onResults on every camera frame, roughly 30 times a second. The game ticks on a setInterval every 200 milliseconds, so 5 times a second. That means the direction can be rewritten five or six times between one snake movement and the next, and only the last write before a tick has any effect.

In practice this feels fine, and it is the reason the game is forgiving: you have a sixth of a second of wobble while changing your hand shape, and only where your fingers land at the end of it counts. It was not designed that way so much as it fell out of using two independent timers.

Known limits, honestly

These are things I can see in the code rather than problems I chased down, so I am listing them as limits rather than as a debugging story.

  • The finger check assumes an upright hand. It compares y coordinates only. Rotate your hand ninety degrees and a raised finger is no longer above its knuckle, so the count collapses. A rotation invariant version would compare each fingertip's distance from the wrist instead.
  • Gesture is read every frame, with no debounce. Moving from one finger to three passes through two on the way, and if a tick lands during that transit the snake turns the wrong way. Requiring the same count on two or three consecutive frames would remove it.
  • There is a dead variable. lastGesture is initialised to 3 and never read again. It looks like the beginning of exactly the debounce described above.
  • Food can spawn inside the snake. The new position is a plain random tile with no check against the body, so on a long snake it can appear underneath it.

What I would do next

The debounce is the highest value change for the least work, and lastGesture is already sitting there waiting for it. Requiring two matching frames before committing a direction would cut the accidental turns without making the controls feel sluggish, because the game only reads direction every 200ms anyway.
